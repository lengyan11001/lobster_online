# 账号安全：修改密码 / 换绑手机号 —— 影响评估（先评估，未动代码）

评估时间：2026-09-18　范围：`lobster-server`（云端账号）+ `lobster_online`（桌面端）

## 0. 一句话结论

**账号本体就是手机号**：`User.email = "<手机号>@sms.lobster.local"`（非默认 OEM 再带品牌后缀）。
所以"换绑手机号"不是改一个联系方式字段，而是**改账号主键标识**，会连带影响 6 条链路。
其中只有两条会真出事：**① 小程序/H5 的设备绑定**、**② 品牌固定代理**；其余属于"要迁移/要提示"。

## 1. 现状证据（手机号 = 账号）

| 事实 | 位置 |
|------|------|
| `User` 表**没有** phone 字段，唯一键是 `email` | `lobster-server/backend/app/models.py:17` |
| 手机号→账号邮箱：`<mobile>@sms.lobster.local` | `services/brand_context.py:298`、`api/auth.py:139,181` |
| 品牌后缀：`+brand-<mark>`（同号在不同 OEM 是不同账号） | `services/brand_context.py:20`、`api/auth.py:142` |
| 手机号密码登录 / 验证码注册登录 | `api/auth.py:546`、`api/auth.py:641` |
| 登录账号可用"账号或手机号"，手机号会被归一化成账号邮箱 | `api/auth.py:167`、`api/auth.py:335` |
| **默认密码 = 手机号后 6 位**（注册时写入） | `api/auth.py:684`、`api/auth.py:386`、启动补齐 `create_app.py:786` |
| 桌面端本地也有一份同样的解析（本地登录/账号识别） | `lobster_online/backend/app/api/auth.py:138-167` |

## 2. 与手机号强绑定的工作清单

### 🔴 A. 小程序 / H5 与 online 账号的绑定（最严重）

- 表：`mobile_device_bindings(user_id, phone, device_id, openid, ...)`，`phone` 是"手机端 → 桌面 online 账号"的唯一链接 —— `models.py:1137-1152`
- 写入：`api/mobile_client.py:760-772`（`/api/mobile/devices/bind`，手机号来自微信授权或短信验证）
- 解析：`api/mobile_identity.py:40-73` `online_user_for_mobile_user()` / `online_user_for_mobile_binding()`
- **依赖它的功能（H5 全站）**：
  - `api/h5_home.py:63,73,96`（设备/算力/首页数据）
  - `api/h5_personal_settings.py:141`（个人设置）
  - `api/h5_agent_management.py:202,240,289`（代理/员工管理）

**换绑影响**：绑定行里的 `phone` 不会自动更新 →
1. 桌面换到新号后，手机端仍解析到**老手机号的账号** → 桌面/手机两套数据（设备、素材、任务、余额各看一半）；
2. 更严重：老手机号日后被**别人**注册时，小程序会把对方账号当成"你的 online 账号" → 跨账号读取（隐私事故）。

> 结论：换绑必须同步更新该用户（及其设备绑定）的 `mobile_device_bindings.phone`；并且注册/绑定时要清理指向该手机号的历史绑定。

### 🔴 B. 品牌固定代理（按手机号判定）

- `services/brand_context.py:24-28`：`daka=13927485337`、`hikong=13510019898`、`jinghai=13554848542`
- 判定：`is_brand_fixed_agent()` `brand_context.py:262-271`；`api/billing.py:98-101` 也按手机号反查代理账号

**换绑影响**：这三个号一换绑，代理身份（全品牌可见、充值归属）立刻失效。建议：**这几个号禁止自助换绑**（要换走后台改配置 + 迁移数据）。

### 🟠 C. 注册/安装赠送积分（唯一键含手机号）

- 表：`installation_signup_bonus_claims`，`UniqueConstraint(phone, brand_mark)` —— `models.py:1614-1626`
- 逻辑：`api/installation_slots.py:114-145`；调用 `api/auth.py:695,1222,1298`、`api/mobile_client.py:152`

**换绑影响**：
1. 老手机号仍占着旧记录，新手机号是"干净"的 → **同一人换号可重复领赠送**（漏洞）；
2. 该函数在"记录已存在"分支会把 `user.credits = 0`（`installation_slots.py:131,143`）→ 若换绑流程误触发，会**清空余额**，必须避免。

### 🟠 D. 管理后台 / 运营脚本按手机号找人

- `api/manage.py:70-86 _user_by_phone()`（仅 `brand=bihuo`），使用于 `manage.py:335,439-440,1483-1484`
- 脚本：`scripts/query_phone_user_remote.py`、`scripts/ssh_grant_user_credits.py`、`scripts/set_user_admin_and_credits.py`

**换绑影响**：按老手机号查不到人（要改用新号）。数据安全无影响，但客服/发积分流程要更新口径。

### 🟡 E. "默认密码 = 手机号后 6 位"的隐含约定

- `api/auth.py:684`（注册即用手机号后 6 位当密码）、`api/auth.py:386`（老账号补齐）、`api/mobile_client.py:143`

**换绑影响**：换绑不会自动改密码（`password_initialized=True` 就不再重写）→ 一直用默认密码的用户，换绑后"新号后 6 位"登不进去，容易被当成故障 → 页面必须提示"换绑不会改密码"。
另：小程序 openid 账号（`mobile_client.py:204 _new_wechat_user`）**没有可用密码**（`password_initialized=False`），H5 的"输入原密码修改密码"对这类会话不成立，需要走"设置密码"分支。

### 🟡 F. 展示/记录里的手机号（读时派生，不致命）

`api/admin.py:466,489,3080,3135,3183`、`api/generation_records.py:89`、`api/ip_content_studio.py:6860`、`api/manage.py:343`
都是把 `email` 前缀当手机号展示 → 换绑后历史记录会显示新手机号（归属仍按 user_id），对账口径需同步。

### ✅ 明确不受影响的

| 维度 | 说明 |
|------|------|
| 积分/流水/订单/代理佣金 | 全部 `user_id` 维度（`CreditLedger.user_id`、`RechargeOrder.user_id`…） |
| 素材/任务/生成记录/设备槽位 | `user_id` / `installation_id` 维度（`UserInstallation`、`installation_slots.py`） |
| 微信 openid、企业微信 userid、速推 token、语言/OEM 品牌 | 与手机号无关 |
| 桌面端本地数据 | 按 token/user_id 存；本地只有登录时做一次"手机号→账号"解析 |
| 短信限流 `SmsSendLimit.mobile`、`AuthChallenge.target` | 临时数据，换绑无害（旧号的 challenge 顺手清掉即可） |

## 3. 三个可选方案

**方案 1（推荐，真换绑）**：原密码校验 + 新手机号短信验证码 →
① `User.email` 改成新手机号（保留品牌后缀）；② 同步 `mobile_device_bindings.phone`；
③ 迁移/锁定 `installation_signup_bonus_claims`（防重复领奖）；④ 清旧号 challenge；⑤ 写审计日志；
⑥ 固定代理号禁止自助换绑；⑦ 换绑后强制重新登录。

**方案 2（最稳，不动账号本体）**：新增 `User.phone`（联系方式）作为展示与找回，`email`（登录名）不变 →
风险最小，但"账号还是老手机号"，且新号默认不能登录（除非登录同时按 `User.phone` 匹配）。

**方案 3（不推荐）**：换绑=新建账号+搬数据 → `user_id` 变了，积分/订单/流水/记录全要迁，成本与风险都最高。

## 4. 需要拍板的 3 件事

1. **老手机号是否释放**（能否被别人注册）→ 决定 A 的兜底强度（建议释放，但注册时清理指向该号的旧绑定）
2. **固定代理那三个号是否允许换绑**（建议：禁止）
3. **赠送积分口径**（建议：跟着新号走，并阻止重复领取）

## 5. 结论

- 改密码：现有 `/auth/set-password` **不校验原密码**（`api/auth.py:567-579`）；已按口径新增 `/auth/password/change`（用户自助改密必须原密码），
  **管理后台重置密码不需要原密码**（只有用户自己改密才需要），对小程序会话走"设置密码"分支。
- 换绑手机号：**必须一并处理 A + C**，否则会出现"手机端看不到自己的设备/数据"甚至跨账号访问。

---

## 6. 实施结果（2026-09-18 已上线）

**口径确认**：方案 1 直接换绑；老手机号释放；品牌固定代理三个号禁止换绑；赠送积分跟手机号走、一个号只赠送一次。

**服务端 `lobster_server`（commit 837a967 + ae47bca）**
| 接口 | 说明 |
|------|------|
| `POST /auth/password/change` | 用户自助改密：**必须原密码**，新旧不能相同 |
| `POST /auth/phone/change/send-code` | 换绑发码：原密码 + 新号可用性校验（固定代理号/被占用直接拒） |
| `POST /auth/phone/change` | 原密码 + 新号验证码 → 改 `user.email`、迁移 `mobile_device_bindings.phone`、迁移/补齐 `installation_signup_bonus_claims`、清老号 challenge |
| `POST /admin/api/reset-password` | **不需要原密码**（按最新口径回退了二次确认） |

- 拒绝规则：固定代理号（daka 13927485337 / hikong 13510019898 / jinghai 13554848542）→ 403；目标号被同品牌其它账号占用 → 409；品牌不一致 → 403。
- 老手机号释放后：其待用短信 challenge 已清；别人注册老号只会拿到一个全新账号（不会继承任何数据）。
- **关联方式约定**：新增数据关联一律用表内 ID（user_id 等），不再用手机号；本次只迁移上述两处历史遗留手机号字段。
